# 데모 시나리오 (약 8분)

라인이 정상 운전하는 화면에서 시작해, 이상을 하나 일으키고 **감지 → AI 조치 지시서 → 작업자 조치 결과 → 해제 → 같은 이상 재발 시 과거 이력 반영**까지 보여 준 뒤 구조를 설명하는 흐름입니다.

## 시작 전 체크리스트

- [ ] Mosquitto 서비스, PostgreSQL 실행 중
- [ ] `scripts\start-demo.ps1` 실행 → 대시보드 상단 **● 실시간 연결** 확인
- [ ] 5분 정도 미리 띄워 두기 (차트에 5분치 추세가 차 있어야 보기 좋다)
- [ ] 이상 주입용 터미널을 하나 열어 두기
- [ ] 이전 테스트 알람이 너무 많으면 정리 (아래 "초기화" 참고)
- [ ] 네트워크가 없어도 전부 로컬에서 동작함을 확인 (와이파이 끄고 한 번 실행)
- [ ] 만일을 대비한 백업: 화면 녹화 1개, 주요 화면 스크린샷 3장 (정상 / 위험 알람 / 지시서 팝업)

## 진행

### 1. 한 줄 소개 — 30초

> "화장품·세제 공장의 미니 라인을 가상으로 만들고, 센서 데이터가 들어와서 이상을 잡고, AI가 설비 매뉴얼을 찾아 조치 지시서를 쓰는 데까지 한 흐름으로 연결해 봤습니다."

README의 구성도를 한 번 보여 준다: **센서 → MQTT → Spring Boot/PostgreSQL → AI 에이전트 → 대시보드**.

### 2. 정상 운전 화면 — 1분

- 설비 4대 카드: 원료 탱크 2, 배합기, 충진기. 모두 **● 정상**.
- 각 차트는 최근 5분 추세이고, 점선은 경고(노란색)·위험(빨간색) 기준선이다.
- 상단 **● 실시간 연결**: 서버가 SSE로 밀어주는 값이라 새로고침 없이 1초마다 갱신된다.
- 차트에 마우스를 올려 시각·값 툴팁을 보여 준다.

### 3. 이상 #1 배합기 진동 — 2~3분 (핵심)

```powershell
powershell -File scripts\inject.ps1 mixer_vibration
```

시간 순서대로 보이는 것:

| 시점 | 화면 | 말할 것 |
|---|---|---|
| 약 3초 | 배합기 진동 차트가 오르고 노란 기준선(4.5)을 넘음 → **▲ 경고** | "ISO 10816 기준으로 4.5mm/s를 주의 구간으로 잡았습니다." |
| 약 6초 | 7.1 넘음 → 카드 테두리 빨강, **■ 위험**. 같은 알람이 위험으로 상승. 활성 알람에 "AI 지시서 작성 중…" | "알람을 새로 만들지 않고 같은 알람의 심각도를 올립니다. 알람이 쏟아지지 않게 하려고요." |
| 약 12~16초 | 오른쪽 **AI 조치 지시서**에 경고 · 위험 지시서가 차례로 생김 (Claude). 키가 없으면 템플릿이라 바로 생김 | "알람이 MQTT로 나가면 에이전트가 매뉴얼을 검색하고, Claude가 그 구절을 근거로 지시서를 씁니다." |

**활성 알람 → "AI 조치 지시서 보기"** 를 눌러 팝업을 연다.

- 추정 원인 → 점검 절차 → **즉시 조치(위험)** → 안전 주의사항 → 에스컬레이션 순서.
- 경고 지시서와 비교하면 조치가 다르다: 경고는 "회전수를 낮추고 관찰", 위험은 "즉시 정지 + 잠금·표지(LOTO) 후 점검".
- 맨 아래 **근거 문서**: 어떤 매뉴얼의 어떤 섹션을 근거로 썼는지와 검색 점수. "AI가 왜 이렇게 판단했는지 추적할 수 있게 남깁니다."
- 키가 있으면 지시서 목록에 **Claude (LLM)** 으로 표시되고, 맨 위에 **상황 판단**이 붙으며 항목마다 *(근거: 점검 절차)* 가 달린다. "LLM이 쓰되, 매뉴얼에 없는 걸 지어내면 그 답은 버리고 템플릿으로 씁니다. 근거 번호를 검증하거든요."

약 30초 기다리면 값이 내려오고 알람이 **해제**된다. 알람 이력 표에서 발생값 → 최악값 → 지속 시간을 보여 준다.

### 3-1. 작업자 피드백 → 다음 지시서에 반영 — 1~2분

알람이 해제되기를 기다리는 동안 위험 지시서 팝업 맨 아래 **작업자 조치**에서:

1. **지시서 확인** → 목록의 상태가 미확인 → **조치 중**으로 바뀐다. "작업자가 읽었다는 기록부터 남깁니다."
2. 확인한 원인은 매뉴얼 선택지에서 **베어링 마모·윤활 부족**을 고른다 ("원인 이름을 매뉴얼 기준으로 맞춰야 통계가 흩어지지 않습니다"). 조치 내용 `그리스 보충, 커플링 볼트 재조임 후 재가동`, 결과 **해결** → **조치 완료**. 목록에 **완료 · 해결**, 같은 알람의 경고 지시서는 **함께 처리**로 바뀐다. "한 알람에 지시서가 두 장 나와도 작업자는 한 번만 처리하면 됩니다."
3. 알람이 해제된 뒤 다시 주입한다.

```powershell
powershell -File scripts\inject.ps1 mixer_vibration
```

4. 새 지시서 요약 끝에 "과거 유사 조치 1건 참고". 팝업을 열면 맨 위에 **과거 유사 조치 이력**과 **우선 확인: 지난번 해결된 원인 '베어링 마모·윤활 부족'** 이 보인다.

> "매뉴얼에는 일반적인 원인이 다 나열돼 있지만, 이 설비는 보통 뭐가 원인이었는지는 현장 사람만 압니다. 그 기록을 다음 지시서의 근거로 다시 넣어서, 쓸수록 이 공장에 맞는 지시서가 되게 했습니다."

5. 화면 아래 **조치 이력 요약** 표를 보여 준다. 배합기 진동의 이상 횟수, 해결률, 평균 처리 시간, 주요 원인 칩.

> "기록이 쌓이면 어느 설비가 자주 서는지, 원인이 뭐였는지가 표로 나옵니다. 정비 계획이나 예비품 준비를 이 데이터로 할 수 있습니다."

### 4. 이상 #2 다른 설비 — 1분

```powershell
powershell -File scripts\inject.ps1 tank_overheat
```

- 이번에는 원료 탱크 2 온도. 에이전트가 **다른 매뉴얼(MAN-TANK-TEMP-01)** 을 찾아 스팀 밸브 차단, 원료 이송 중지, 품질 확인 같은 탱크용 조치를 쓴다.
- "같은 배합기라도 진동과 과전류는 다른 매뉴얼을 찾습니다." 시간이 되면 `mixer_overcurrent`도 보여 준다.

### 4-0. 추세 기반 조기 경보 — 1분 (선택)

```powershell
powershell -File scripts\inject.ps1 mixer_bearing_wear
```

- 약 20초 뒤 배합기 카드에 **◆ 예측** (점선 테두리)과 "기준 ≥ 4.50 까지 약 N초" 카운트다운. 활성 알람 패널 맨 위에도 예측 항목.
- 약 40~50초 뒤 실제 경고 → 알람에 **"◆ 발생 N초 전에 추세로 예측됨"** 이 남는다.

> "기준값만 보면 넘은 다음에야 압니다. 최근 추세로 '이대로 가면 25초 뒤 경고'를 먼저 알려서 정비 준비 시간을 법니다. 신호마다 평소 흔들림을 배워서 노이즈로는 울리지 않게 했습니다."

※ 백엔드를 띄운 직후 2분 정도는 평소 수준을 배우는 시간이라 예측이 늦을 수 있다.

### 4-1. 교대 인수인계 리포트 — 30초~1분 (선택)

상단 **교대 인수인계** → 최근 **1시간** → **리포트 작성**. 약 10초 뒤 리포트가 채워진다.

- 맨 위 집계(알람 몇 건, 남은 지시서 몇 건)는 코드가 센 값, 아래 문장은 Claude가 알람 · 지시서 번호를 근거로 쓴 것.
- **다음 교대가 이어서 할 일**에 아직 확인 안 된 지시서와 진행 중인 알람이 잡힌다.

> "다크팩토리는 사람이 적어서 교대할 때 무슨 일이 있었는지 정리하는 게 더 중요해집니다. 그걸 버튼 하나로 만들었고, 숫자는 코드가 세서 AI가 숫자를 틀릴 일이 없게 했습니다."

### 4-2. AI 질문 · 매뉴얼 개선 제안 — 1분 (선택)

- 상단 **AI에게 질문** → 예시 "배합기 진동 원인이 주로 뭐였어?" → 약 10초 뒤 답변과 근거(WO 번호, 매뉴얼 섹션, 통계).
- 일부러 "작년 3월 충진기 고장 이력 알려줘" → "재료에 없어 답할 수 없다". "모르는 건 모른다고 답하게 했습니다."
- 조치 이력 요약 표의 배합기 진동 **매뉴얼 개선 제안** → 조치 기록과 매뉴얼을 비교한 초안. 모든 변경 제안에 현장 기록(WO) 근거가 붙는다.

> "현장 조치가 쌓이면 매뉴얼이 현장을 못 따라가는 부분이 보입니다. AI가 초안을 쓰고, 반영은 사람이 검토해서 합니다."

### 5. 구조 설명 — 1~2분

화면을 띄운 채로 핵심 설계만 짧게:

1. **OT/IT 분리** — 센서는 MQTT 토픽에만 발행한다. 실제 설비로 바꿀 때는 PLC·OPC UA 게이트웨이가 같은 토픽에 넣으면 된다.
2. **커밋 후 이벤트** — 알람을 DB에 커밋한 다음에 에이전트와 화면으로 보낸다. 순서가 꼬이지 않는다.
3. **설명 가능한 RAG** — 매뉴얼을 섹션 단위로 검색하고, 근거와 점수를 지시서에 남긴다. 지금은 TF-IDF라 모델 없이 오프라인에서도 돈다. 다음 단계는 임베딩 + pgvector.
4. **사람이 최종 판단** — AI는 설비를 직접 건드리지 않고 지시서까지만 쓴다.
5. **LLM 교체 지점** — 지시서 생성기는 인터페이스 하나라, LLM을 붙여도 검색·저장·화면은 그대로다.

### 6. 마무리 — 30초

> "다음으로는 LLM 생성기, 쌓인 조치 이력으로 반복 고장 원인을 찾는 분석, 그리고 실제 설비 프로토콜 연동을 해 보고 싶습니다."

## 예상 질문

**왜 MQTT인가요? Kafka는요?**
현장 장비·게이트웨이 쪽 표준에 가깝고 가볍습니다. 공장 한 곳 규모의 실시간 관제에는 브로커 하나로 충분합니다. 여러 공장 데이터를 모아 분석하는 단계가 되면 MQTT 뒤에 Kafka를 붙이는 구성을 생각합니다.

**왜 TF-IDF인가요? 임베딩이 더 좋지 않나요?**
매뉴얼이 몇 개 안 되고 용어가 정해져 있어서, 문자 n-gram만으로도 맞는 매뉴얼을 찾습니다. 모델 다운로드나 GPU 없이 오프라인으로 돌고, 점수를 설명하기도 쉽습니다. 매뉴얼이 늘고 "표현은 다르지만 뜻이 같은" 질의가 많아지면 임베딩으로 바꿉니다. 검색 함수 하나만 바꾸면 됩니다.

**오탐이나 알람 폭주는 어떻게 막나요?**
설비·지표마다 활성 알람을 하나로 유지하고, 해제할 때는 기준보다 5% 더 정상 쪽으로 돌아와야 하도록 히스테리시스를 둡니다. 다음 단계로는 일정 시간 지속돼야 발생시키는 조건이나 다변량 판단을 넣을 수 있습니다.

**LLM이 틀린 조치를 쓰면요?**
매뉴얼 구절과 과거 조치에 번호를 붙여 주고, 모든 항목에 근거 번호를 달게 합니다. 근거가 없거나 준 적 없는 번호를 쓰면 그 답은 버리고 매뉴얼 템플릿으로 씁니다. 그리고 AI는 지시서까지만 쓰고, 작업자가 확인하고 조치 결과를 남기는 흐름이라 최종 판단은 사람이 합니다.

**실제 공장에 붙이려면 무엇이 더 필요한가요?**
설비 프로토콜 게이트웨이(OPC UA, Modbus), 태그·설비 마스터 관리, 인증과 권한, 이력 데이터 보관 정책, 그리고 현장 작업자가 실제로 쓰는 화면(모바일·태블릿)입니다.

## 초기화 (선택)

알람·지시서 기록을 비우고 깨끗한 화면에서 시작하려면, 데모 전용 DB에서 아래를 실행합니다.

```sql
TRUNCATE work_order, alarm, sensor_reading RESTART IDENTITY;
```

데이터가 비면 차트도 비므로, 초기화한 뒤 5분 정도 띄워 두고 시작합니다.
